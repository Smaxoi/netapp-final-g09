# 多人幾A幾B網路對戰系統（BC/1.0）

網路應用軟體設計 期末專題 · 組別 `G09`

<https://github.com/Smaxoi/netapp-final-g09>

以 Python 3 實作一支可同時扮演**伺服器（莊家）**、**人類玩家客戶端**與 **AI 代理人**的程式，
嚴格遵守課程定義的 **BC/1.0 應用層通訊協定**，使任何兩組的程式都能跨越網際網路直接連線對玩。

> 本專題的核心要求是**互通性**：全班各組的程式只要遵守同一份協定，就必須能彼此連線、
> 共同完成一局多人猜數字遊戲。

## 遊戲規則摘要

- **秘密數字**：四個 ASCII 數字字元，四位**兩兩相異**，允許首位為 0（例 `0275`）。合法數字共 10×9×8×7 = **5040** 個。
- **幾 A 幾 B**：
  - `A` = 數字與位置皆正確的個數
  - `B` = 數字正確但位置不對的個數
  - 合法回報須滿足 `A + B ≤ 4`，且**不可能出現 3A1B**，故合法回報恰有 14 種。
- **回合流程**：輪到的玩家喊出一個合法四位數 → 其餘每位存活玩家依自己的秘密回報幾 A 幾 B
  → 伺服器**收齊後一次公開**所有回報 → 回報 `4A0B` 者被猜中而淘汰（可繼續觀看）。
- **名次**：最早被猜出者名次最後，最後留在場上者獲勝。採標準競賽排名（並列同名次，下一名次跳號）。

| 終局狀態 | 意義 | 名次規則 |
|---|---|---|
| `SURVIVOR` | 終局仍存活且揭示驗證通過 | 第 1 名 |
| `GUESSED` | 被猜中淘汰且揭示驗證通過 | 排在存活者之後，淘汰回合越晚越前 |
| `FORFEIT` | 斷線、回報逾時、連續未喊數達上限 | 排在所有 `GUESSED` 之後 |
| `DQ` | 回報自相矛盾、揭示與承諾不符、未揭示 | 取消名次 |

## 公平機制：承諾—揭示

伺服器**不知道任何人的秘密數字**，因此採用密碼學的承諾—揭示（commit–reveal）機制，
使別組撰寫的莊家程式不必被信任。

開局時每位玩家產生 16 位元組的隨機鹽值，只送出 SHA-256 承諾值：

```python
import hashlib, secrets

salt = secrets.token_hex(16)          # 32 個小寫十六進位字元
commit = hashlib.sha256(f"{secret}:{salt}".encode("ascii")).hexdigest()
```

> 鹽值**必須**用 `secrets` 模組產生，不可用 `random`。
> 測試向量：秘密 `0275` + 鹽值 `2eb6594c74b9b9d71e2d9b5bd14300df`
> → `6b05c8fe4113aa24833fcbd089d33f0fe48ff68eb0a7d7fff87319a394338721`

**三道防線**讓不實回報必然被發現：

1. **公開一致性檢查（每回合）**：伺服器為每位回報者計算 5040 個合法數字中仍與其所有歷史回報相容者；候選集合變成空集即當回合取消資格。
2. **淘汰時揭示**：被判定猜中者立即送出秘密與鹽值，伺服器驗證承諾值並以揭示的秘密重算其每一筆歷史回報。
3. **終局揭示**：終局仍存活者同樣揭示並接受驗證。

## 系統架構

星狀的主從式架構。莊家就是伺服器，所有玩家（包括 AI 代理人）都以客戶端身分經由 TCP 連入。
伺服器只擔任裁判，從頭到尾不知道任何人的秘密數字。

```
                      ┌────────────────┐
                      │  bc.py server  │  莊家／裁判
                      └───────┬────────┘
            ┌─────────────┬───┴───┬─────────────┐
            │             │       │             │
      ┌─────┴─────┐ ┌─────┴────┐ ┌┴─────────┐ ┌─┴────────┐
      │ client 人 │ │ ai  BOT-1│ │ ai BOT-2 │ │ 他組程式 │
      └───────────┘ └──────────┘ └──────────┘ └──────────┘
          遠端           本機子行程              跨組連入
```

- 只繳交**一支 `bc.py`**，以子命令決定身分。
- 伺服器以 `--bots K` 指定 AI 玩家時，自動以**子行程**啟動 K 個本組程式的 `ai` 身分，名稱依序為 `BOT-1` 至 `BOT-K`。
- AI 子行程與遠端玩家走**完全相同**的協定，差別只在於連線來自本機。

### 對局狀態機

```
LOBBY ──► COMMIT ──► PLAY ──► END ──► OVER
 大廳      承諾       對局    終局揭示   結束
```

| 階段 | 伺服器送出 | 接受的客戶端訊息 | 離開條件 |
|---|---|---|---|
| `LOBBY` | `WELCOME`、`LOBBY` | `HELLO` | 人數達 `--players`，或莊家輸入 `start` 且至少 2 人 |
| `COMMIT` | `GAME_START`、`COMMITS` | `COMMIT` | 全員送出承諾或逾時；剩不到 2 人以 `ABORTED` 結束 |
| `PLAY` | `TURN`、`GUESS_MADE`、`TURN_RESULT`、`REVEAL_REQUEST`、`REVEALED` | `GUESS`、`FEEDBACK`、`REVEAL` | 存活玩家不超過 1 人，或回合數達 `max_turns` |
| `END` | `REVEAL_REQUEST`、`REVEALED` | `REVEAL` | 存活者完成揭示或逾時 |
| `OVER` | `GAME_OVER` | 無 | 關閉所有連線；`--games` 未滿則回到 `LOBBY` |

`CHAT`、`PING`、`PONG`、`BYE` 在完成 `HELLO` 後的**任何階段**都可以送出。

## 執行方式

程式進入點一律為儲存庫根目錄的 `bc.py`，以子命令決定身分。

### 伺服器（莊家）

```bash
python bc.py server --port 5040 --players 4 --bots 2
```

| 選項 | 預設值 | 意義 |
|---|---|---|
| `--host` | `0.0.0.0` | 伺服器監聽的位址 |
| `--port` | `5040` | TCP 埠號 |
| `--players` | `2` | 本局玩家總數（2–6，含 AI）；人數到齊即自動開局 |
| `--bots` | `0` | 伺服器自動啟動的 AI 玩家數（0 ≤ K ≤ N） |
| `--guess-timeout` | `60` | 喊數時限（秒） |
| `--feedback-timeout` | `60` | 回報時限（秒） |
| `--commit-timeout` | `30` | 送出承諾值時限（秒） |
| `--reveal-timeout` | `15` | 揭示時限（秒） |
| `--max-turns` | `120` | 回合數上限 |
| `--max-skips` | `3` | 連續逾時未喊數幾次即視為棄權 |
| `--games` | `1` | 連續舉辦的局數，0 表示不限 |
| `--log-dir` | `logs` | 日誌目錄 |

所有時限選項都接受小數秒數（例如 `1.5`）。
伺服器另提供主控台命令 **`start`**，讓莊家在至少 2 人加入時提早開局。

### 人類玩家客戶端

```bash
python bc.py client --host 127.0.0.1 --port 5040 --name G09-小明 --team G09
```

### AI 代理人

```bash
python bc.py ai --host 127.0.0.1 --port 5040 --name G09-AI --team G09 --quiet
```

| 選項 | 預設值 | 意義 |
|---|---|---|
| `--host` | 必填 | 伺服器位址 |
| `--port` | `5040` | TCP 埠號 |
| `--name` | 必填 | 玩家名稱，1–20 字，同局不可重複 |
| `--team` | `G00` | 組別代碼，例如 `G07` |
| `--quiet` | — | （僅 `ai`）減少輸出 |

> 12/22 跨組對玩時，玩家名稱須以組別代碼開頭：`G09-AI`、`G09-小明`。

## 介面操作說明

### 人類玩家客戶端操作流程

1. **設定秘密數字**：開局時輸入四位相異數字，或按 Enter 隨機產生；程式自動計算並送出承諾值（鹽值只存在記憶體中）。
2. **輪到喊數**：依提示輸入四位數，程式先在本地檢查格式，並顯示剩餘時間。
3. **需要回報時**：畫面顯示對方的喊數與自己的秘密，**預填自動計算的幾 A 幾 B**，確認後送出；若修改數值會要求再次確認。
4. **揭示**：收到 `REVEAL_REQUEST` 時由程式自動完成，不需人類介入。
5. **被淘汰後**轉為觀看模式，仍可看到所有公開資訊與聊天。

等待輸入時仍會即時顯示新訊息，並自動回應 `PING`。

## 日誌格式

伺服器將每局收送的每一則訊息寫入 `--log-dir` 目錄中的一個 **JSON Lines** 檔案，
檔名包含 `game_id`，**一局一檔**，UTF-8 編碼，每筆紀錄寫入後立即 flush。

```json
{"ts": 1791474054.218, "dir": "send", "peer": "p1", "msg": {"type": "TURN", "turn_id": 1, "guesser": "p3", "alive": ["p3", "p2", "p1"]}}
```

| 欄位 | 意義 |
|---|---|
| `ts` | Unix 時間（秒，可含小數） |
| `dir` | `send` 或 `recv` |
| `peer` | 對方的 `player_id`（完成 `HELLO` 前則寫 `IP:埠號`） |
| `msg` | 訊息物件本身；無法解析的輸入以 `{"raw": "…"}` 記錄 |

> 日誌目錄中**只能有伺服器的日誌**。客戶端以相同格式另行保存自己的日誌，位置自訂，
> 但**不得寫入伺服器的日誌目錄**。

## AI 策略

AI 為每位存活對手維護一個候選集合，並以**每一則 `TURN_RESULT`** 更新（不只是自己喊數的結果）。

- **基準策略**：鎖定候選最少的對手，從其候選中挑選能把候選切成最多組的數字，
  即 Kooi (2005) 的「最多劃分」（most parts）準則。
- **多人局的取捨**：一次喊數同時測試所有對手，但只有喊中某人的候選才有機會當場猜中他，
  因此必須在「累積對全場的資訊」與「立即猜中一人」之間取捨。

實驗結果（至少 100 局，對參考 AI 的勝率、平均名次與平均回合數）詳見設計報告。
